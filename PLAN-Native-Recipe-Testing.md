# Native recipe testing and coverage ownership

Status: implemented locally, 2026-10-01. Directory discovery and native runtime
fixtures are implemented in c2j. Recipe behavior suites have moved to declarations;
the separate fixture server, client, Python drivers and shell runners are removed.
Compatibility CI now runs native directory discovery against the companion
recipes commit. The legacy runner preparation and migration patches are removed.
Publish the referenced recipes commit before running the coupled c2j CI revision.

## Goal and ownership

Deliver this in two stages: **c2j first, recipes second**. Recipe authors must be
able to run their complete declared suite with `c2j test`, without maintaining a
server, client program, Python generator, or shell test runner.

| Owner | Responsibility |
| --- | --- |
| c2j | All c2j correctness tests: compilation, CLI behavior, execution, child submission, scheduling integration, replay, workspaces, snapshots, objects, input/review APIs, and the test runner itself. |
| recipes | Declarative tests of the actual recipes: decisions, approval requirements, feedback loops, dependency handling, document/session routing, verification requirements, and merge policy. |
| c2j compatibility CI | Run suites from the recipes repository's default branch with the candidate c2j binary to detect consumer breakage. This supplements c2j's own regression coverage. |
| c2ops | Operation implementation correctness, such as Codex session import/export and CLI invocation. Recipe tests cover how recipes use those contracts. |

A scenario may currently mix these responsibilities. Split its assertions by
owner rather than copying the entire scenario into both repositories. Every
c2j bug discovered through a production recipe needs a minimal reproducer in
c2j; reproducing it must not require the recipes checkout.

“Declarations only” applies to recipe test infrastructure. YAML/JSON cases,
Markdown descriptions, fixture documents, file trees, and recipe fixtures are
appropriate. Moving a Python harness into a YAML `run` block is not a migration.
Production commands that are part of a recipe remain production behavior.

## Findings from the current repositories

- `pkg/recipetest/harness.go` executes the compiler using `testJobContext`.
  `AwaitJobs` and `AwaitDuration` return immediately; submission, restart
  submission, and yielding are unsupported. Passthrough invokes op handlers
  directly, rather than exercising the complete task execution lifecycle.
- `cmd/c2j/internal/testjob/runner.go` already provisions a disposable embedded
  runtime for passthrough dependencies. The root recipe still runs through the
  special context. An `integration_case` label does not currently select real
  durable execution.
- c2j already has runtime fixtures in `pkg/worker/test-fixtures`,
  `pkg/worker/compiler`, `pkg/child/test-fixtures`, and CLI tests. Reuse and extend
  those facilities; do not build another workflow executor.
- The recipes repo's `recipe-tests/jobdb-service` wraps JobDB's in-memory runtime
  in HTTP and adds job-inspection/cancellation helpers. Its Python callers own
  worker processes, polling, termination, restart, and assertions.
- The current `/recipes` checkout also contains `recipe-tests/review-client`,
  object-session fixtures, eight default-suite Python drivers, and shell runners
  for other suites. The migration includes these, not just the five Python
  suites in c2j's older compatibility pin.
- Some `.scenario.md` files, including build/evolve, describe cases generated by
  Python rather than containing runnable cases. File discovery alone would
  falsely suggest those recipes already have native coverage.

The current CI investigation identified three concrete issues to retain as
regressions: detached c2ops checkout cannot satisfy `@main`; a separately pinned
fixture server uses an older JobDB protocol than c2j; and JSON helpers fail on
CEL map literals used as history defaults. Fix and test these during stage 1;
do not solve them by weakening the compatibility gate.

## Stage 1 — c2j runtime coverage and native test support

### 1. Establish the migration inventory

Record each existing test statement/case, its assertion, destination, and
replacement case ID. Inspect current recipes, not only the old compatibility
revision. Keep this inventory with c2j while building the replacement framework;
use it to update recipe test statements during stage 2.

Initial mapping:

| Existing recipes coverage | c2j-owned regression | Recipe-owned declaration |
| --- | --- | --- |
| `verify-cli-framework.sh`, inline/include validation smokes | CLI parsing, compile/validate/run consistency, source resolution and exit codes | Recipe validity and published input/output contracts |
| `verify-dependencies.py`, child orchestration smokes | Broker submission, includes in submitted children, lineage, waiting, cancellation, replay and duplicate prevention | What the recipe does for successful, failed, cancelled, and unmerged dependencies |
| `verify-consultations.py`, `verify-implementation-consultations.py` | Workspace isolation, pinned bases, parent restoration and wait/replay | When to consult, questions/context sent, handoff approval and feedback routing |
| `verify-development-lifecycle.py`, child artifact forwarding smoke | Child snapshot exclusion, artifact provenance, retrieval after worker replacement, parent/child merge mechanics | Build/evolve approvals, evidence export and merge eligibility |
| `verify-native-reviews.py`, `review-client` | Public input API validation, review/document retrieval, attachments and receipt replay | Which documents/questions a recipe asks to review and how answers change its flow |
| `verify-object-sessions.py`, object-session fixtures | Generic object checkpoint immutability, branching, retrieval, validation and artifact visibility | Session-object routing across recipe phases; Codex adapter mechanics belong to c2ops |
| `verify-default-recipes.py`, `verify-review-contract.py`, other scenario suites | Any isolated compiler/template/runtime defect they reveal | Recipe routing, schema/document contracts, verification commands, acceptance and rejection paths |

Include negative cases and currently expected failures in the inventory. Mark a
case obsolete only when the corresponding production behavior was deliberately
removed; document the reason.

### 2. Put engine regressions in c2j

Reduce runtime assertions to small parent/child recipes and deterministic test
ops in the relevant c2j packages. Extend existing tests where they already
establish the same guarantee. Keep production build/evolve implementations out
of these fixtures.

Required regression groups:

- Child submission through the broker, compiled includes, child identity and
  lineage, children completing before/during a wait, failure and cancellation.
- Parent suspension and replacement worker replay: no repeated submission or
  completed op side effects, and unchanged dependency/artifact references.
- Fresh explicit workspaces with shared descendants, return to the parent,
  consultation discard, child merge followed by parent continuation/merge,
  and snapshot ownership for both implicit and explicit workspaces.
- Nested template histories through both returned values and JSON helpers,
  including empty maps, artifact refs, nulls and large integers.
- Generic object branches from an earlier checkpoint, unsuccessful branches,
  new workers/jobs, invalid references and hidden internal artifacts.
- Native input/review behavior using public library APIs, including multiple
  documents, response attachments, invalid answers and replay after a response.

Use the same JobDB dependency as c2j. Where an actual process boundary is needed
to prove broker/CLI/restart behavior, c2j tests own the temporary server and child
processes. Use the existing remote server implementation and public library
inspection APIs rather than reproducing the fixture's custom HTTP routes.

### 3. Add real runtime execution to the native test runner

Keep the current fast mock-oriented execution for existing suites. Add an
explicit, versioned way for integration cases to select execution through the
real runtime. Do not silently change existing `integration_case` semantics.
Settle the exact schema spelling in the first implementation change and provide
a compatibility test for existing suites.

The runtime-backed runner must:

1. Create isolated case state: JobDB, tenant/jobs, work directories and temporary
   cell Git repositories. Load fixture files and additional recipes using normal
   source/include resolution, relative to the declaring file.
2. Submit the recipe through normal submission/compilation and execute normal
   task workers. Exercise actual artifact persistence, object storage, Git
   snapshots, child jobs, waits, input tasks, completion and failure paths.
3. Run child workers automatically within the case. Support deterministic
   fixture outcomes for an external dependency without requiring a fake polling
   service. A completed child must be represented by a real persisted result.
4. Provide a temporary loopback JobDB service only when test subprocesses need
   one. Its dependency and lifecycle belong to c2j; recipe authors never supply
   a binary, URL, module version, or startup command.
5. Keep runtime/configuration scoped to the case. Do not inherit a live parent
   broker or use a user's persistent database. Avoid process-global environment
   rewrites shared by concurrent cases. Resolve authored op selectors normally;
   CI must not replace branch refs or override their source repositories.
6. Cancel workers, stop services and retain diagnostics on every exit path,
   including a timeout. Apply a deadline to the whole case and its children.

Expose the capability through the c2j library and CLI. Reuse production runtime
and worker code; do not reproduce JobDB scheduling in `testJobContext`.

### 4. Supply a small declarative fixture vocabulary

Extend the existing case/mocks/assertions model, rather than creating a second
test language. Add only capabilities required to replace the inventoried cases:

| Requirement | Native facility |
| --- | --- |
| Seed a cell or provide review documents | Inline data or relative fixture-file/tree references; runner creates disposable repositories and artifacts. |
| Replace a model or another external op | Match authored node/selector plus invocation occurrence; return declared outputs, artifact files and, where necessary, worktree edits. |
| Simulate an op that submits children | A declared fixture effect submits named fixture recipes through c2j's normal child submission path. No inline Python calling `c2j submit`. |
| Route opaque session objects | Runner creates named opaque checkpoints through the real object API and binds them into declared responses; authors do not manufacture storage keys or rollouts. |
| Answer a human review | Match a pending input node and supply fields, answers and existing attachment refs/files through the public input API. |
| Exercise dependency outcomes | Bind a dependency to a fixture recipe/outcome and, when needed, release it at a declared observable checkpoint. |
| Assert recipe behavior | Extend existing assertions to cover op inputs/call counts, review questions/documents, child requests/results, file changes and ordering at checkpoints. |

Effects must pass through real persistence/snapshot/child APIs. Mock only the
chosen external work, not the wait, merge or storage behavior being tested.
Mock selection must use durable invocation identity: replay cannot consume the
next scripted response or produce a second child. Scope matches to the job and
node so concurrent children cannot accidentally consume each other's responses.

Use observable checkpoints rather than arbitrary sleeps. Keep low-level lease
faults, process killing and scheduler controls in c2j's Go regressions; recipe
authors should express “approval is required before merge” or “a failed
dependency requests feedback,” not manipulate leases or worker PIDs.

Default offline fixtures must not unexpectedly invoke live model services.
Explicitly selected live suites may exercise real external integrations and
declare their requirements. Missing required capabilities must produce a clear
failure or reported skip according to the suite policy, never a false pass.

### 5. Make a repository suite runnable without a script

Use recursive directory discovery and self-contained suite declarations. No
manifest is required. Discover `*.test.yaml`, `*.test.yml`, `*.test.json`, and
`*.scenario.md` in deterministic order. Each suite declares its recipe target;
recipe and fixture paths resolve relative to the suite file.

```sh
c2j test validate --directory recipe-tests
c2j test run --directory recipe-tests --out-dir .c2j/test-results
```

Reuse existing case selection, parallelism, assertion results, JSON events and
exit conventions. Report every discovered suite, invalid declaration and
selected case. Empty discovery/selection and required failures return nonzero;
attempt all selected suites unless fail-fast is requested. Keep single-file and
single-case execution available. Suites requiring live services declare that
requirement and require explicit `--include-live` selection; report omissions.
Optional tags/groups can follow demonstrated need. A central manifest is deferred.

Retain worker logs, assertions, relevant job/task events and artifact references
in one result directory, including failures before a worker starts. CI should
invoke this command and upload that directory, without interpreting results in
Python or shell.

### Stage 1 acceptance and release gate

- All migrated c2j guarantees have local regressions using minimal fixtures;
  the c2j correctness suite works without fetching the recipes repo.
- Native tests run a multi-cell parent/child scenario, a real review with
  attachments, and session-object routing using only declarations and fixture
  data. Runtime regressions separately prove replacement-worker replay.
- Existing suites retain their documented behavior. Compile, validate and run
  agree on source resolution and supported declarations.
- Parallel cases are isolated; timeout/error cleanup and result retention are
  tested. Unexpected mocks, unused required responses and invalid assertions
  cannot silently pass.
- A deliberate recipe-policy defect fails a declarative case. A deliberate
  child-replay or snapshot defect fails a c2j runtime regression.
- Add user documentation and update the c2j recipe-testing skill. Publish the
  version supporting the new declarations before stage 2 requires it.

Keep the existing compatibility suite enabled during this stage. Temporary
fixture preparation may align its server dependency and source refs, but that
is a bridge, not the target architecture. No recipe infrastructure is deleted
until its replacement coverage has passed.

## Stage 2 — declarative recipe tests and repository cleanup

1. Set the supported minimum c2j version. Make every suite self-contained and
   discoverable under its test directory, including other recipe families and
   explicitly marked live integrations; do not silently drop suites called by shell.
2. Convert build/evolve routing, consultations, dependency outcomes, reviews,
   verification/merge decisions and session routing into runnable declarations.
   Use the actual production recipes and native fixtures instead of copying and
   rewriting their graphs in Python. Replace descriptive placeholder scenario
   files with executable cases.
3. Convert the remaining new-ticket, jobs, examples and superpowers suite
   runners. Keep recipe-specific positive and negative assertions. Move CLI,
   object-store, input API and runtime assertions to their stage 1 counterparts.
4. For each c2ops implementation assertion, record a c2ops-owned destination and
   verify replacement coverage before removing it. Do not add a Codex emulator
   to the public c2j test schema just to preserve an adapter test. Any required
   c2ops change is a separate handoff; only `/src` and `/recipes` are in scope.
5. Compare old/new case inventories and outcomes per family. Account for every
   test statement, including expected failures and removed production behavior.
   Keep both paths temporarily if a replacement is not yet equivalent.
6. Remove `recipe-tests/jobdb-service`, `recipe-tests/review-client`, Python
   generators/drivers/model emulators, custom polling/process management and
   shell suite runners once their replacements pass. Remove their Go modules,
   uv/Python test dependencies and generated-case documentation as well.
7. Update author guides, test statements and skills to the native command.
   Update `.c2j/mandate.md` to reflect the agreed ownership: recipe test
   declarations belong here; reusable testing infrastructure belongs in c2j.

Recipe correctness tests need no Go toolchain or Python harness. Real recipe ops
can still require Git, a container runtime or other declared execution tools;
live model tests still require their ordinary service access. This migration
does not claim that all recipe execution becomes dependency-free.

### Stage 2 acceptance and compatibility CI

- From a clean recipes checkout, an installed compatible c2j can discover,
  validate and run every required suite directly from declarations.
- No recipe test requires an independently compiled service/client, generated
  YAML, shell runner or Python orchestration. Static fixture data remains.
- All recipe-owned assertions are mapped and passing; c2j correctness coverage
  remains in c2j. c2ops handoffs are resolved before their old tests are removed.
- Point c2j compatibility CI at the recipes default branch and run the newly
  built c2j with directory discovery; use public checkout authentication defaults.
  Record the selected recipes SHA and use normal op resolution.
- Remove the temporary server dependency adjustment, fixture runner setup,
  `recipes-verification-export.patch`, and c2ops checkout/branch/URL overrides.
  Recipes own their op versions; CI must not patch their dependency selection.
- Keep compatibility a required CI check and retain complete failure output.
  The summary job aggregates results; the native report identifies the failed
  case and its reason.

## Suggested delivery slices

1. **c2j:** coverage inventory, immediate regressions/fixes, minimal runtime
   fixtures and a shared internal runtime test helper where needed.
2. **c2j:** runtime-backed native cases, deterministic external-op/child fixtures
   and isolation/replay tests for the runner itself.
3. **c2j:** review/object/file fixtures, required assertions, directory discovery,
   documentation and a release passing the stage 1 gate.
4. **recipes:** migrate declarations family by family, update test statements,
   remove equivalent infrastructure and publish the new suite revision.
5. **c2j:** enable default-branch compatibility checks and remove transitional setup.

Keep changes and commits separate by repository. Stage 2 starts after stage 1's
capabilities are available; the final compatibility workflow update is a consumer
update, not a second implementation of the testing framework.
