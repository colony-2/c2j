# Artifacts from values: implementation plan

## Agreed scope

Add `kind: value` artifact references with `format: text|json`, `value`, and an optional `name`. An explicit artifact binding supplies its destination filename; scalar artifact inputs require `name`. Text is exact UTF-8 without an added newline. JSON uses the existing JSON encoding plus one trailing newline. Missing `value` is invalid; JSON null is valid.

Resolve expressions using existing recipe scopes. Preserve the resolved content as data when forwarding through includes and outputs. Recognize value sources only at artifact boundaries, never by recursively reinterpreting ordinary business objects.

Generated inputs remain value-backed references. Small invocations use ordinary task JSON; invocations above 128 KiB carry their resolved input, artifact bindings, and preparation data in one attachment through the existing task-input artifact channel. The worker restores that payload before validation and execution. This avoids JobDB's 256 KiB application-JSON limit. The executing worker writes them into its inbox before invoking the consumer. The local file is disposable and can be recreated from the descriptor on another worker. No new JobDB preparation record, versioned context, or writer task is needed; the attachment uses normal task-input persistence. Existing stored/external references retain their behavior.

Reuse descriptors through existing inputs, vars, and outputs. Do not introduce an `input_artifacts` namespace or permanent artifact-story inspection for generated inputs.

Explicit `outputs.artifact_refs` exports use the existing job-result artifact persistence path. Inline recipes can return value-backed references for subsequent consumers; an enclosing job can export them explicitly. Human-review documents use existing attachment persistence because another client must open them. This is distinct from disposable inbox materialization.

## Implementation

1. Extend artifact references with the value variant, strict source decoding, serialization, and filename handling.
2. Reuse current artifact binding validation, collision checks, typed input normalization, and inbox file writing.
3. Accept value references in artifact/artifact-map recipe parameters; preserve ordinary object semantics.
4. Support explicit result exports and review documents using existing artifact publication facilities.
5. Add a user guide and regression/integration coverage, run affected suites and compilation, then commit.

The complete feature exceeds approximately 100 implementation lines: the basic materialization path is small, but strict validation, typed references, and result/review integration need separate adapters. Keep those adapters local and reuse existing persistence and file-writing code.

## Verification

- Exact Unicode/whitespace/template-looking text and JSON/null/empty values.
- Invalid formats, missing values, unknown/mixed fields, unnamed scalar sources, unsafe paths, and destination collisions.
- Existing artifact sets with files named `kind`, `format`, and `value`.
- Multi-megabyte materialization into native and packaged-op inboxes; no content in process argv or environment.
- Forwarding through recipe scopes, typed artifact fields/maps, and ordinary objects that resemble descriptors.
- Recreating files on retry/worker replacement and replay without executing completed tasks.
- Explicit exported artifacts and human-review documents readable through existing artifact APIs.
- Validation creates no files; no private chapter export is committed.

## Approved transport adjustment

The initial 512 KiB lifecycle test failed with `chapter_application_payload_too_large`: 524,981 application bytes against the default 262,144-byte limit. The user approved carrying the payload through the existing task-input artifact channel. The task envelope retains execution metadata and a small attachment name; workers restore the resolved payload before processing it. Small invocations retain their existing representation. Explicit result exports similarly attach their bytes and use filename markers in result JSON, which child-result readers resolve to stored references.

This feature does not remove existing limits on ordinary job inputs, task commands, or op outputs. Large documents generated by expressions use the attachment handoff; embedding a multi-megabyte literal in ordinary job inputs or the task declaration is still subject to those limits. Changing general job payload limits is outside this feature.
